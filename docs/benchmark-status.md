# État du benchmark v1

`data/annotations/questions.jsonl` contient 45 questions de développement en brouillon (`author_provisional`) et 45 questions de validation revues par le propriétaire du projet. Le développement reprend les 15 questions de calibration et ajoute 30 questions candidates. Les annotations de validation conservent la source de la revue, les statuts, les affirmations attendues et les passages canoniques cités.

La commande `constitution-evidence audit-questions` affiche l'inventaire et les défauts de structure. Elle vérifie notamment les identifiants, la séparation des familles, les champs d'annotation et les offsets des preuves dans le corpus actif. Elle ne peut pas établir qu'une interprétation juridique est correcte. Le seuil prévu reste 45 familles dev, 45 validation et 90 test. Les 90 questions test revues sont conservées dans un fichier **local, ignoré par Git**, `data/annotations/test-candidates.jsonl`. Elles ne doivent pas servir au choix des méthodes. Les 45 questions dev restent à annoter.

`constitution-evidence question-review-packet` crée `reports/question-review.md`, un dossier de travail local avec les questions dev, les articles candidats, le texte canonique et les liens vers les pages du PDF. Pour validation, utiliser `constitution-evidence question-review-packet --split validation --output reports/question-review-validation.md`. Le dossier du test local est généré avec `--questions data/annotations/test-candidates.jsonl --split test --output reports/question-review-test.md`. Ces dossiers sont ignorés par Git. Ils ne valident aucune question automatiquement.

Pour chaque famille ajoutée, suivre [le guide d'annotation](annotation-guide.md), vérifier les preuves sur le PDF et le corpus canonique, puis seulement attribuer `review_status: "reviewed"`. La revue des 135 questions validation/test a été accréditée par le propriétaire du projet sur la base d'un audit assisté ; elle n'est pas une double revue indépendante. Les questions test doivent être gelées avant leur exécution ; leurs sorties ne servent pas à choisir les méthodes. Une seconde passe par l'auteur doit être signalée comme telle si aucun autre relecteur n'est disponible.

Une fois l'audit complet, les expériences de recherche sur dev et validation peuvent être exécutées, la configuration sélectionnée sur validation, puis `release-readiness` doit être relancé. Aucun résultat de `v1.0` ne doit être annoncé tant que le test réservé et le jugement des réponses ne sont pas terminés.
